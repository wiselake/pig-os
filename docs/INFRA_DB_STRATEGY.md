## 2. 왜 옮겼나 (2026-08-25)

Supabase 무료 티어 → EC2 로컬 PG. **비용 절감이 아니라 운영 불가 때문이다.**

증상이 단계적으로 악화됐다:

| 시점 | 상태 |
|---|---|
| 2026-08-24 | 풀러 세션 포화 → 커넥션 수립 4~6초 → 대시보드 31초 |
| 2026-08-25 오전 | 로그인 17초 / 가입 29초 / 농장생성 500 |
| 2026-08-25 정오 | `ConnectionDoesNotExistError: connection was closed in the middle of operation` |

마지막 것이 결정적이었다 — **풀러가 쿼리 실행 도중 연결을 끊는다.** 애플리케이션에서
고칠 수 없다. 풀 크기·keepalive·캐시를 바꿔가며 재기동했지만 증상만 흔들렸다.

한도도 실측으로 막혀 있었다: `EMAXCONNSESSION: max clients are limited to pool_size: 15`.
대시보드에서 Pool Size 를 30 으로 올려도 **반영되지 않았다**(프로젝트 재시작 후에도).

이전 후 실측:

| 지표 | Supabase 풀러 | EC2 로컬 PG17 |
|---|---|---|
| 커넥션 획득 + `SELECT 1` | 쿼리 도중 절단 | **0.001s** |
| 전체 덤프(같은 143M 데이터) | **67분 35초** | 29초 |
| 로그인 | 17초 / 500 | 0.34초 |
| 동시 클라이언트 한도 | 15 | 200 |

> ⚠️ **이전만으로 다 해결되지 않았다.** 옮긴 뒤에도 대시보드는 5.67초였다.
> 원인이 두 개였고(풀러 + `farrowings` by-sow 인덱스 누락) 하나만 고친 상태였다.
> 인덱스 추가 후 0.57초. **증상 하나에 원인 하나라고 가정하지 말 것.**

## 3. 무엇을 포기했나 (정직하게)

이 문서의 이전 판(2026-06)은 EC2 self-host 를 **"백업·장애복구·보안패치 전부 수동 →
운영 리스크. 비추"** 로 분류했다. 그 판단 자체는 틀리지 않았다. 우리는 그 리스크를
**받아들이기로 선택한 것**이지, 리스크가 사라진 게 아니다.

| 잃은 것 | 현재 대응 | 남은 위험 |
|---|---|---|
| 관리형 자동 백업 | 크론 덤프(§4) | **PITR 없음** — 최악 24시간 손실 |
| 오프사이트 보관 | ★ **끊겨 있다 (2026-09-16 실측)** — S3 `pigos-db-backup/pigos-db/` 객체 6개가 전부 2026-08-25 자다. 어떤 백업 스크립트도 S3 에 올리지 않는다(`grep -rn s3 ~/pigos/ops/` 0건). 8/25 분은 손으로 올린 것 | **로컬 단독** — DB 와 같은 EC2·같은 디스크. 인스턴스가 사라지면 함께 사라진다. `DR_RESTORE_REHEARSAL_20260916.md` §3 |
| 이중화·failover | ❌ 없음 | 단일 장애점. 다운타임 = 복구 시간 |
| 보안 패치 자동 | ✅ `unattended-upgrades` enabled (실측 확인) | PG 메이저 업그레이드는 여전히 수동 |
| 리소스 격리 | ❌ 타 프로젝트와 공유 | 다른 프로젝트가 메모리를 먹으면 같이 느려진다 |

~~**오프사이트 백업은 해결됐다**(2026-08-25).~~ ★ **2026-09-16 정정 — 하루만 참이었다.**
버킷 `pigos-db-backup` 과 EC2 역할 `pigos-ec2-backup-role` 은 정상이고 같은 버킷의
`wiselake-console/` 은 매일 올라온다. 그러나 **PigOS 백업 스크립트에 업로드 단계가 없다** —
8/25 의 6개 객체는 설정하던 날 수동 업로드였고 그 뒤 22일간 0건이다. "전체·스키마·증분
모두 업로드된다" 는 서술은 사실이 아니었다. 근거·권고 패치: `docs/runs/DR_RESTORE_REHEARSAL_20260916.md` §3.

★ **복원은 2026-09-16 에 처음으로 실제 검증됐다** — 당일 전체 덤프를 격리 PostgreSQL 17 에
복원해 59테이블·141,408 sows·531,841 farrowings·alembic head 일치·ORM 조회까지 확인했다
(`DR_RESTORE_REHEARSAL_20260916.md`). 그 전까지 "백업이 있다" 는 복원 가능하다는 뜻이 아니었다.

남은 최대 위험은 **이중화 부재**다 — DB 가 죽으면 복구 시간만큼 서비스가 멈춘다.
백업이 있으니 데이터는 지켜지지만 다운타임은 못 줄인다. 유료 고객이 생기면 §5 의
RDS 전환 트리거가 걸린다.

## 4. 백업 체계 (유일한 방어선)

| 종류 | 크론 | 명령 | 크기·시간 |
|---|---|---|---|
| schema | 매일 03:15 | `ops/backup_db.sh schema` | 37K |
| full | 매일 03:40 | `ops/backup_db.sh full` | 143M · 약 30초 |
| 증분 | 매일 15:05 | `ops/backup_incremental.sh 2` | 20K · 약 22초 |

- 대상은 **`DATABASE_URL`(앱이 실제로 쓰는 DB)** 이다. 이전 직후 `MIGRATION_DATABASE_URL`
  을 우선하던 옛 로직 때문에 죽은 Supabase 를 백업할 뻔했다 — 원칙을 뒤집어 고쳤다.
- 증분 백업은 원래 Supabase egress 쿼터(5GB) 때문에 존재했다. 로컬 PG 는 전송 비용이
  없어 전체를 매일 돌리고, 증분은 그 사이를 메우는 역할로 재정의했다.
- `-deploy` 태그가 붙은 덤프는 보존기간 정리에서 제외된다(되돌릴 지점).
- 복원 절차·검증은 `ops/ROLLBACK.md` §E.

## 5. 향후 방향

### 지금 — EC2 로컬 PG 유지
데이터 627MB, 커넥션 18/200, load 0.04. **용량·성능 여유는 충분하다.**
지금 필요한 건 스케일이 아니라 **§3 의 구멍을 메우는 것**이다.

우선순위:
1. ~~S3 오프사이트 백업~~ ✅ 2026-08-25 완료
2. ~~복원 리허설~~ ✅ 2026-08-25 완료 (24.1초·ERROR 0, `ops/ROLLBACK.md` E-4 에 절차화)
3. **버킷 수명주기·버전관리** — 매일 143MB 가 무한정 쌓인다. 1년 ≈ 52GB.
   권장: 30일 후 Glacier IR / 180일 후 삭제 + 버전관리로 실수 덮어쓰기 방어
4. 디스크·커넥션 모니터링 알림
5. **S3 복원 경로 검증** — 다운로드는 훅 정책(AWS 조회만 허용)으로 미실시.
   head-object 크기 일치까지만 확인했다. 리허설 때 한 번은 실제로 받아봐야 한다.

### 다음 — AWS RDS PostgreSQL (ap-northeast-2) 전환 트리거
아래 중 **하나라도** 걸리면 검토한다:

- 유료 고객이 생겨 **다운타임이 계약 문제가 될 때** (단일 장애점 해소)
- DB > 20GB 또는 EBS 여유 < 20% (현재 25G/48G 사용)
- 타 프로젝트와의 리소스 경합이 실제로 관측될 때
- 규제·감사에서 관리형 백업·암호화·감사로그를 요구받을 때

전환 비용: pg_dump/restore + `DATABASE_URL` 교체. **데이터가 적을 때 옮기는 게
유리하므로 트리거를 기다리다 늦지 않게 한다.** 이번 이전으로 절차는 이미 검증됐다
(143M 복원 24.7초).

### 되돌아가기 — Supabase
`.env` 에 `SUPABASE_DATABASE_URL` 을 보존해 뒀다. 다만 **2026-08-25 12:20 이후 쓰기는
로컬에만 있다.** 되돌리려면 그 사이 데이터 이관이 필요하므로 실질적으로 편도다.

## 6. 의사결정 요약

| 질문 | 결론 |
|------|------|
| 왜 Supabase 를 떠났나? | 비용이 아니라 **운영 불가**(쿼리 도중 연결 절단) |
| 지금 구성으로 버티나? | **O** — 용량·성능 여유 충분. 문제는 **내구성**이다 |
| 가장 급한 것은? | 오프사이트는 해결(S3). 이제 **이중화 부재**(다운타임)와 **버킷 수명주기** |
| RDS 는 언제? | 유료 고객 다운타임 리스크 · DB 20GB · 리소스 경합 중 하나 |
| auto-pause keepalive 는? | **불필요해졌다**(로컬 PG 는 정지하지 않음). 무해하나 §7 참조 |

## 7. 이전으로 무의미해진 것들

| 대상 | 상태 |
|---|---|
| `api/app/jobs/keepalive.py` (auto-pause 방지 일일 ping) | 무해하지만 **목적 소멸** — 로컬 PG 는 무활동으로 정지하지 않는다 |
| `DB_KEEPALIVE_INTERVAL` (풀 keepalive) | 프로덕션 `0`(비활성). 풀러 대응용이었고 오히려 경합을 키울 수 있었다 |
| 무료 티어 용량 500MB / 대역폭 5GB 감시 | 해당 없음 |

정리는 별도 작업으로 둔다 — 지금 지우면 되돌아갈 때 다시 만들어야 한다.
